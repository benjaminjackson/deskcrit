# deskcrit

`deskcrit` is a Claude Code plugin with a design critic. Its `design-critic` skill starts a Claude agent that reads a picture of a design, checks it against a catalog of guidelines from an approved reading list, and writes a ranked crit in prose that explains each finding as what the viewer experiences, plus a JSON work order that a coding agent can act on. Its `crit-loop` skill runs a fix loop on that work order. The npm package `deskcrit` is only the development tooling of this repository: the guideline packs and their fixtures, the build of the skill's references, and the evaluations of the critic. It has no command and no library entry point.

## Where things are

- `BRIEF.md` is the pitch: what the tool is, who it is for, the principles, the risks, and the milestones.
- `GUIDELINES.md` is the catalog of guidelines that the seven first-party packs encode. Each entry has a rule, a source, and a note on how it becomes a question.
- `docs/CONSTITUTION.md` is the coding standards. Read it before you write or review code, and cite its rules by ID (CS-n).
- `docs/PRD.md` is the behavioral specification with stable IDs. It is the source of truth for what to build. If `BRIEF.md` and `docs/PRD.md` disagree, `docs/PRD.md` wins and the disagreement is a defect to report.
- `README.md` is the user-facing guide: what the plugin does, a sample crit, requirements, install steps, how to start each skill, and the commands to develop. Do not treat it as a specification.

Current state: Benjamin Jackson ruled on 2026-11-24 to remove Jev ("Ok! Let's remove Jev. Ruled!"), and crit-mk9.3 removed TypeSafe's Jev model and the `crit` command. The Jev design ended at git tag `jev-spike-final`, and `docs/PRD.md` section 1 records the removal. Under PRD section 7.12 the judge is a subagent critic (FR-77), and the work is milestone M-6.

- `evals/packs-fixture-rules.ts` holds the offline check of the FR-54 fixture rules: `listPackDirectories`, `listFixtureFolders`, `parseAttributionFile`, and `checkPackFixtures`, which reports each fixture file over 2 MB, each image without exactly one `fixtures/ATTRIBUTION.md` entry, each entry without an accepted rights basis or the capture details, and a `pack.yaml` license that differs from the `Pack license:` line. It reads files only and imports nothing from `src/`. `evals/packs-fixture-rules.test.ts` runs it on every folder under `packs/` that holds a `fixtures/` folder, and has one failing case for each rule.
- `evals/pack-thresholds.test.ts` checks that every criterion of a first-party pack that has `pass_when` also has `fail_when`. Reason: by step 4 of the verdict rule, such a criterion without `fail_when` gives `fail` when no predicate matches, so a criterion meant to warn at most could fail (EV-5, FR-25). It reads every `packs/*/pack.yaml` except the folders whose name starts with `_`.
- `evals/plugin-skill.test.ts` checks `plugin/skills/crit-loop/SKILL.md` (FR-69, FR-82). Each line must stop on its missing input and not on the usage error. It checks that each `<design-critic folder>` path in the skill exists, and that each code span that looks like a JSON field is a field of the work-order or facts schema in `schemas/`. It also checks that no agent file or SKILL.md of either skill uses a buyer, sale, price, or trial word as an example (crit-cgl, bd memory critic-no-buyer-framing), allowing only the listed real terms, each of which must still be in its file. Review trigger: a skill needs one of these words outside an example, or Benjamin Jackson changes the ruling. It also checks, with file reads only, that the crit-loop skill fixes every finding of the work order, lists the findings it skips, and counts the Smaller things list in its stop rules, that the recheck sends every Smaller things item to the fixer, that the FR-82 row records the decision, and that the user text drops the old stop rule (crit-73l).
- `plugin/skills/crit-loop/SKILL.md` is the fix loop of FR-82. Round 1 runs the design-critic skill, with `measure.mjs` when the page source or a URL is available, and gets a work order. Round 1 picks the `measure.mjs` flags and every round passes the same ones, so every round has the same viewports, and the critic and the recheck critic get every screenshot of the facts file. Each later round fixes every finding of the work order, the ranked ones first and then the ones with `rank` null, naming each one it skips at the stop, checks each element a fix adds or restyles against the template tells and uses a plain form over a stock one, fixes a short last line on that element only and never on a selector that other elements share (crit-y75), captures again the same way, and starts a fresh recheck critic on the before image, the after image, and the last work order. The work-order agent then turns the recheck into the next work order. When the person gave a brief, round 1 writes its Brief block to `brief.md` in the loop folder, and every recheck and later work order gets the current text of that file. That block includes the project brief `.deskcrit/brief.md` merged by design-critic step 1, no later round reads the project brief, a decision the person says holds for the whole project also goes into `.deskcrit/brief.md`, and the stop names each project line the loop overrode (FR-88, crit-crj.1). When the person settles a finding in chat, the loop writes the decision on the Fixed line of `brief.md`, creating the file when the loop has no brief, does not fix that finding, and undoes a change it already made to its element in that round; the recheck then marks the finding settled (FR-82, FR-87, crit-deh). When the person gave the real thing that the design mocks, round 1 writes each path to `real-thing.txt` in the loop folder, and every recheck gets one `Real thing:` line per path (FR-77, crit-321). When a crit or recheck requests a fact with a `Fact needed from the maker:` sentence, the round asks the person for every requested fact in one question before the work order, writes the answers to `brief.md`, never asks again for a fact the person did not give (it lists each one in `facts-asked.txt` in the loop folder), and leaves a finding whose whole fix is such a fact out of the stop rules (FR-82, crit-cbt). It stops when the recheck lists no finding, ranked or under "Smaller things", apart from the findings it skips (the fact set-aside, settled, the deck pattern, the opposite of a higher finding, out of scope by the brief's Ask or Stage unless it is a WCAG failure or a broken Fixed entry, and the line that a mock could not be checked against the real thing), or when two rounds in a row close nothing (crit-73l), and it keeps the line "Fix the design, not the score". It holds no verdict or threshold logic (FR-69). A deck or a flow of screens runs as a set (crit-3wg): one capture per slide, one measure run on `<deck file>#<k>` for slide k, contact-sheet mode with the consistency check every round, fixing only the ranked breaks of the set work order, the rechecks and a fresh set critic started in one message, and a set work order that the work-order agent writes from the set critic's crit, given to the next set critic as `Last set work order:` so it marks each break closed or open; when a slide finding and the set critic ask for opposite changes on one element, the deck pattern wins (Benjamin Jackson, 2026-11-25); the set stops when no slide has a finding left, ranked or smaller, and the last line is `Breaks: none` or names only thin-screen breaks set aside for a fact nobody gave, or when two rounds in a row close nothing. The set critic may request one fact, for a thin-screen break, and the round's question includes it (crit-1kh).

When the caller gives the path of the real thing that the piece mocks, step 2 adds one `Real thing:` line per path as the last lines before `You critique only.`, and the main thread never opens it. `agents/critic.md` is what that agent is told; its step 3 says how the critic uses each brief field, and how it judges a mock against the real thing or says under "Smaller things" that it could not (FR-77, crit-321). Its section "Your inputs" says what every agent of the skill may read: its prompt, each file the prompt names by path, and a closed list of files those files name. An agent never lists or searches a folder, never reads project records, and ignores a user message that a harness relays. ## How we build: the Phoenix rules

This project follows Chad Fowler's regenerative software series, "The Phoenix Architecture". The goal is that any module can be deleted and rewritten from the specification and the evaluations, so the knowledge is written in the specification and the evaluations and not only in the code. Numbers in brackets are Fowler's post numbers from https://chadfowler.com/regenerative-software/.

- Keep four durable things, because deleting any one of them makes regeneration impossible [Fowler 21]. The specification is `docs/PRD.md` plus the pack, facts, and work-order JSON schemas. The evaluations are the durable test suite and the fixture set under `evals/`. The boundaries are the skill files and the JSON schemas the skills write. The provenance is the commit and pull request history, which names the PRD IDs.
- Treat the specification as the source and the code as derived [Fowler 21]. When a behavior should change, change `docs/PRD.md` first, then regenerate the code to match. Never edit the PRD to describe what the code happens to do, because evidence is not intent and only a human ratifies a new requirement [Fowler 25].
- Regenerate instead of patching [Fowler 8]. Prefer rewriting a whole module from its PRD section and its evaluations over editing it in place. A hand edit that bypasses the specification means the specification is incomplete, so fix the specification and then regenerate [Fowler 19].
- Before trusting or rewriting any code, ask: if this changed in a rewrite, would I care? If yes, it belongs in `docs/PRD.md` or a durable evaluation, not only in code. Odd retries and edge-case branches usually record a real failure; move the lesson into the PRD first [Fowler 15, 23, 26].
- Keep each module at component grain [Fowler 17]. A module must be understandable in about ten minutes, verifiable at its own boundary, and rewritable in a day. If a module fails one of those, split it or fix its boundary.
- Give each piece of state exactly one owner [Fowler 17]. The fixture set and the label files are written only by people, through review. The evaluations read them and never write them. See PRD AC-5 and AC-7.
- Delete abstractions that do not pay rent, and prefer plain repetitive code over clever indirection [Fowler 5, 9]. Before adding a layer, name the second use that justifies it.
- Write durable evaluations at the boundary of the skill [Fowler 7]. The durable forms here are the checks of the skill's command lines and references, JSON schema validation of what the skill writes, the fixture-rule checks, and the critic evaluations that replay saved crits against human labels. They must still pass if the code is rewritten in another language. Unit tests that mock internals are disposable and may be deleted without ceremony.
- Agents write durable tests and the person reviews them in the pull request like any other change [Fowler 11]. The one hard stop: never weaken, skip, or delete an existing durable test to make a change pass. Propose that change and wait for approval.
- Layer independent checks [Fowler 13]. Schema validation, the detection and compare evaluations, and the repeat-run check each catch different faults, so do not drop one because another passes.
- Keep the slow layer slow [Fowler 14]. The pack YAML schema and the JSON schemas in `schemas/` are the protocol between this project and its human and agent users. Change them only by adding optional fields and flags, and record each change in the PRD (AC-2).
- Attach a reason and a review trigger to every constraint [Fowler 26]. When you add a rule to this file or to the PRD, write why it exists and what would make it wrong. A rule without a reason is a fence nobody dares remove, and a wrong rule steers a generator more confidently than a missing one.
- Record provenance in every commit and pull request [Fowler 13, 19]. Name the beads ticket id and the PRD IDs the change implements or changes. Tickets live in beads (`bd`): one epic per milestone, one subticket per unit of work, PRD IDs as labels in the form `prd:FR-25`, and the acceptance field quoting the PRD acceptance criteria (PRD OQ-14). IDs have the prefixes G for goals, NG for non-goals, P for personas, US for user stories, FR for functional requirements, NFR for non-functional requirements, JC for the removed Jev and TypeSafe constraints, AC for architecture rules, EV for evaluations, R for risks, M for milestones, and OQ for open questions. A change to `docs/PRD.md` ships in the same pull request as the code change it describes.
- Relocate rigor instead of dropping it [Fowler 11, 26]. Do not accept generated code because it runs. Read it, check it against the PRD section it implements, and say in the pull request what you checked.

## Product rules that must not be broken

`docs/PRD.md` sections 9 and 10 are the rules that must not be broken, together with FR-45 (every criterion cites a source that states the rule, or `Common sense` with a reason), G-4 (fix hints written by people), and NG-5 (no content linting). Read them before changing a skill or a pack.

## Stack and conventions

- The language is TypeScript on Node for the evaluations and the fixture renderer. The skill scripts are plain `.mjs` files that use Node's own modules only, so the installed plugin needs no install step, and `scripts/build.rb` needs Ruby 3.0 or later.
- `sharp` is used by the crop tests and the scripts that render evaluation images.
- Vitest runs the tests, and Biome lints and formats. Reason: Vitest runs TypeScript with no extra build step, and Biome is one tool with no plugins to manage. Reconsider when one of them cannot do a job the PRD requires. `docs/CONSTITUTION.md` CS-2 holds the details.
- Do not restate coding style here. `docs/CONSTITUTION.md` holds it, and the naming, comment, and commit-message rules in the user's global `CLAUDE.md` also apply.

## Docs hygiene

- Check every prose document you change with the slop judge before you commit. The command is `sloplint check --judge --markdown -o json --register "a coding agent building deskcrit" <file>`. The judge sends the file text to api.typesafe.ai. On 2026-10-23, Benjamin Jackson approved sending `BRIEF.md`, `docs/PRD.md`, this file, and pack READMEs to the judge, on 2026-10-24 he added `GUIDELINES.md`, and on 2026-11-25 he added `README.md`, so these files need no further consent. Ask before you send any other file. Use the same reader string for every file.
- The judge key is already configured on this machine. Do not look for it, do not print it, and do not read `.env`.
- Keep this file true. When a rule here stops being true, delete it in the same pull request that makes it false. Do not add a rule that is not true today, because a wrong instruction steers a generator more confidently than a missing one [Fowler 26].
- Keep `README.md` and `plugin/README.md` true, the same way `docs/PRD.md` stays true. A pull request that changes what a user installs, runs, or sees updates them in the same pull request: a skill name or what starts it, an install step, a requirement or its version, an output file or where it is saved, a script flag or exit code that the READMEs name, an npm script, or a top-level folder. Before you merge, check each command, path, and flag the READMEs name against the code. Reason: the README is the first and often the only document a user reads, and a step that no longer works sends a new user into a setup that fails with no hint why. Review trigger: user documentation moves to a separate site, or the READMEs stop naming commands and paths.
- Do not keep a second hand-written copy of the specification. Documents other than `docs/PRD.md` point to it and do not restate it [Fowler 25].
