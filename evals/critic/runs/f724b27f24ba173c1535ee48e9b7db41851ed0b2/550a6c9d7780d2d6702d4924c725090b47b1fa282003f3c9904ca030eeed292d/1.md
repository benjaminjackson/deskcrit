**First read.** In both versions the eye lands on "Release notes", then runs down the three entries. In version 1 the eye drops from one bold "Version 4.x, date" line to the next, so the page reads as a list of releases you can skim. In version 2 the eye lands on the title and then meets a single grey block: the version lines are hard to tell from the paragraphs under them, so you read the text in order instead of jumping between releases. Both read as a calm, well-made changelog page for a small photo-editing app.

**What it's for.** My assumption: the release-notes page for Darkroom Lite, where current users check what changed in a given version and when.

**Verdict.** Version 1 does the job better. The only real change is how the version headings are set, and in version 2 that change removes the page's skimming structure. Neither version marks "Release notes" as the current page in the nav, and both set the body text a little too wide.

**What changed, and why it matters**
Version 1 sets each "Version 4.x, date" line in a bold serif, clearly larger than the body, with about 40 px between entries. Version 2 sets the same lines in the regular weight of the body face, at what looks like 19 px against 18 px body text, slightly lighter, with tighter spacing between entries. On a release-notes page the version and date are what the reader scans for ("what's new since 4.1?"). Version 1 gives them a level of their own. Version 2 leaves them one pixel and a slight tint away from the paragraphs, so there are really only two levels on the page: the title and everything else.

**What would move it most** (for version 1, and for version 2 as well)
1. **The nav doesn't mark the current page.** In the top right, "Download · Release notes · Support" are all drawn the same, so nothing tells the reader they are on Release notes except the page title. This is a convention (Nielsen's first heuristic; Laubheimer, NN/g "Menu-Design Checklist", guideline 5). Fix: give the current item one clear cue, such as a bolder weight or an underline.

**Smaller things**
- Body measure: the first paragraph line ("Straighten now finds the horizon… by hand.") runs about 84 characters, beyond Bringhurst's 45 to 75. Narrow the text column to about 620 px, or bump the body size a little. With only two lines per entry this costs little, but it will start to cost as entries get longer.
- Copy: "Presets from version / 3" breaks between "version" and its number at the end of the 4.0 entry. A narrower column may fix this on its own; otherwise use a non-breaking space.

**What's working**
- Version 1's headings work because they differ from the text in weight as well as size (Dair, *Design with Type*, ch. 8). Keep the bold, even if the size step gets smaller.
- The copy is very good for release notes. Each line says what changed for the user, in their own words: "finds the horizon by itself, and you can still drag the line by hand", "about a third faster on older laptops". No ticket numbers and no internal jargon.
- Sans for the site chrome and serif for the content is a clear, intended split, and the left edges (wordmark, title, entries) share one line.

**Where it could go further**
1. Make the date easier to scan than the version number, or set it apart in a lighter grey on the same line. Readers usually ask "what changed lately?" more often than "what changed in 4.1?", and a separate weight or colour within the heading would let both questions be answered at a glance (Dair: multiply the contrasts). Taste.
2. Give the newest release more weight than the archive, for example by setting "4.2" a little more prominently or noting "latest". This page serves the person who just got an update prompt, so the top entry is the one that matters. Taste.

**Couldn't judge from a still.** Hover and focus states on the nav links.
