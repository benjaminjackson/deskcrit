**First read.** The eye goes first to the dark "View site" pill in the top-right corner, then to "Edit post", then to the two paragraphs, and only last to Publish at the bottom right. It reads as a plain, generic CMS post editor. It feels calm and tidy, but it could be anyone's admin screen, and nothing about it speaks to a parish volunteer.

**What it's for.** My assumption: a volunteer who is probably not technical writes a newsletter post, formats it lightly, and publishes it to the parish's readers.

**Verdict.** The page is clean and mostly works, but it is built like a developer's tool rather than for a church volunteer. The biggest problems are that the page's strongest button isn't the one that matters, and the toolbar and Publish button leave the writer guessing what will happen.

**What would move it most**
1. **Two primary buttons, and the wrong one wins.** "View site" in the header and "Publish" under the editor are the same filled, near-black pill at the same 15 px bold. View site comes first in reading order, so it takes the eye before the task does, and a cautious writer may take it for "preview my post." Material Design and Apple's HIG both say one primary action per view, with the rest styled lower. Make View site a plain text link or an outline button, so the only filled button on the screen is Publish. *Convention, with a real cost.*
2. **The toolbar doesn't say what it does, in words this writer uses.** All ten buttons are the same 13 px bold letter on the same grey band. The "I" isn't italic, the "U" isn't underlined, and the "S" isn't struck through, so nothing shows what each one does (Norman, *The Design of Everyday Things*). "“" and "•" are guesswork, and "H1", "H2" and "</>" are web jargon (Nielsen heuristic 2). A code button is no use in a parish newsletter, and underline will read as a link on the web. Draw each style in its own form, call the heading buttons "Heading" and "Subheading", and drop code and underline. If either has to stay, put it behind a "More" control (Nielsen, progressive disclosure). *Defect.*
3. **The writer can't tell what this post is or what Publish will do.** There's no title field, so the post has no headline the writer can see or set. Nothing shows whether this is a new draft, a saved draft, or a live post being edited, or when it was last saved (Nielsen heuristic 1). "Publish" in a *newsletter* tool can be read two ways: put it on the website, or email it to everyone on the list. If the writer expects the first and gets the second, an unproofed post goes to the whole parish and can't be recalled. Add a labelled title field above the body, a status line near "Edit post" (e.g. "Draft, saved 2 min ago"), and a button that names its effect, such as "Publish to site" or "Publish and email subscribers." *Defect.*
4. **The editing line is too long to proofread comfortably.** The text runs across the full 860 px box: the first line, "The spring fair … tea tent", is about 107 characters, well past Bringhurst's 45–75 range. The facts file can't measure text inside a textarea, so this count is by eye. Long lines are where people lose their place, and proofreading is what this screen is for. Cap the text column at about 65–70 characters (roughly 640 px at 16 px), or match the width the published post will use. *Convention.*

**Smaller things.**
- Type scale: five sizes in the facts file (26, 18, 16, 15, 13 px). The 18 px logo, 16 px body and 15 px buttons are too close to read as separate levels. Keep 26 / 16 / 13 and use weight for the rest.

**What's working.**
- **One centred column.** The heading, toolbar, editor and buttons all share the 210–1070 px column, and the button pair sits flush to the editor's right edge, right where writing ends. Keep that alignment.
- **Save draft vs Publish.** Save draft as an outline and Publish as a filled button is the right primary/secondary pairing. The fix in #1 is to make the rest of the page respect it.
- **Comfortable body text.** 16 px Inter at 1.6 line height and 15.8:1 contrast is easy to read for long stretches. Don't trade it away when narrowing the column.

**Couldn't judge from a still.**
- The facts file says the editor is a plain `<textarea>`, which can't show bold or headings. Check in a browser whether B or H1 inserts markup symbols such as `**` or `#` into the text. For this audience that would be a serious problem.
- Whether the toolbar buttons have tooltips or show which formatting is active.

The whole piece: 8 lines, 6 yes, 2 no (every element does a job; same element looks the same)
What matters first: 3 lines, 1 yes, 2 no (one element dominates; distinct text levels)
Arrangement and space: 13 lines, 11 yes, 2 no (only related elements look alike; clear eye path)

Color: 9 lines, 9 yes
