**First read.** In both versions the eye lands on the big serif "Release notes", then moves down the list. In version 1 it stops on three bold version headings, one at a time, so the page reads as a list of three releases at a glance. In version 2 the headings are in regular weight and only slightly larger than the body text, so below the title the page reads as one grey block of six paragraphs. You have to read the text to find where each release starts.

**What it's for.** My assumption: a release-notes page for a small photo-editing app, where existing users scan for their version or the latest one and see what changed.

**Verdict.** Version 1 does the job better. The only real change is the version headings: bold and larger in version 1, regular and near body size in version 2. On a page people scan for a version number, that change decides how fast they find it. Version 1 is clean and works. Its remaining problems are small.

**What would move it most**
1. **Version heading weight (the only change between the two).** In version 2, "Version 4.2, 20 October" and the other headings are set in the body serif at regular weight, only a size or two above the text under them. The step is too small to read as a separate level (Bringhurst: sizes a few points apart read as mistakes, not levels). Nothing else marks the headings: no weight, no colour, no extra space. So a reader scanning for "4.1" has to read each line's opening words. Version 1 uses weight to make the step, which is what Refactoring UI recommends ("bolder, not bigger"). Each heading becomes a clear anchor, and you see three entries at once. **Defect** in version 2: it slows the main task, which is finding a version. Keep version 1's bold headings.

**Smaller things** (for version 1)
- The dates have no year ("20 October", "15 July"). Once the list goes back past one year, readers can't place a release, and even now they can't tell how recent it is. Add the year.
- The space between entries (about 40 px) is only slightly bigger than the space between each heading and its text. More space above each heading would tie each heading to its own text more clearly. This is taste; it already works.
- "Release notes" appears as the active page in the nav, but it looks the same as the other two links. Show which page is current.

**What's working** (version 1)
- The copy is excellent. Each line says what changed for the user in plain words, with real numbers ("about a third faster on older laptops", "more than ten thousand files") and a reassurance where one is needed ("Presets from version 3 are converted the first time you open them"). Keep this voice.
- The type scale is tight: title, version heading, body, plus the sans-serif nav. That's four levels, each with a clear job.
- The text column is about 75 characters wide, at the top of the comfortable range, so it reads easily.

**Couldn't judge from a still.** How the nav links show hover and focus states, and how the column reflows on mobile.

Better: version 1
